# oral-tradition：口头传统

> 判据权威来源：[C-docs-knowledge.md](../C-docs-knowledge.md) · 详解文档供人类讨论，子代理执行口径以族文件为准
> 所属族：C 文档与知识债（[C-docs-knowledge.md](../C-docs-knowledge.md)）· 失败模式：可解性 · 预排：高

## 一览

| 证据等级 | 检测档 | 实例粒度 | rubric 主轴 |
|---|---|---|---|
| **存在性候选**（全类型最弱档：连债的存在都是推断） | LLM 压测点 | 应知条目级（每条未外化的应知知识一个实例） | **踩坑概率**（一维）：知识必要性 × 影响面 |

实例粒度族文件未显式定义，按两步法的比对对象（应知清单条目）取条目级，见「讨论要点」。

## 规则陈述

这条规则说的是：**有些知识，团队里「每个人都知道」，但仓库里零痕迹**——它活在口头传统里：入职面授、standup 顺嘴一提、某个 Slack 频道的三年前消息。判据的正式表述：**应知知识未被 agent 高触达载体（agent 文档 + 注释）覆盖**。

为什么这对 agent 是灾难级？agent 没有「入职」——它拿到仓库的那一刻就是它的入职日，口头传统对它是**绝对真空**。而且这类债有一个独特的恶性质：**agent 100% 踩坑且事后无法归因**。踩坑时 agent 看到的症状是普通的报错或错误结果，它不知道「有一条我没被告知的规则被违反了」，于是它把失败归因到代码本身，在错误的方向上反复尝试——这就是失败模式**可解性**的纯粹形态：不是解得慢，是解不出，且不知道为什么解不出。

为什么证据等级是全类型最弱的「存在性候选」？因为检测的本质是**从无到有的推断**：其他类型的债在仓库里有痕迹（重复的代码、说错的注释、缺失的配置源），本类型的定义恰恰是「无痕迹」——我们能做的只是推断「这里应该有一条知识」。族文件把它排在比 B 族脆性候选再弱一档的位置：连债的存在都是推断，报告语言必须诚实到「存在性候选」。

## 信号与判定

**两步法**：

1. **LLM 生成应知清单**，概念类 / 操作类分层。方法本质是「压测点」：从代码与仓库结构反推「一个不掌握任何口头背景的新人会需要哪些知识」——例如：看到代码里 `if os.environ.get("STAGE") == "prod"` 会问「本地跑的时候 STAGE 该设什么」；看到两个服务共享一张表会问「谁是写入权威」。
2. **比对指定载体**：概念类对照**领域模型文档**（代理上下文文档的概念层），操作类对照 **agent 文档操作层 + 注释**。清单里每一条，去对应载体检索——检索空白即候选。

两条配套规则：

- **「文档在但没写这条」= 外化缺口特例**，记入本类型（文档存在不豁免：判据是「这条知识是否被覆盖」，不是「是否有文档」）；概念类缺口另指向 agent-doc-missing 覆盖不足（那边报「文档质量」的账，这边报「知识缺失」的账）。
- **README / docs 低可达知识接受假阳性**：判据锚定 agent 高触达外化——知识只写在 README 第 300 行，对 agent 仍近似未外化（触达率低），报了不冤。宁可多报，不漏报。

**证据等级落点**：全类型**风险信号档**，报告语言「存在性候选」。fix_suggestion 固定为**外化建议**（写进哪个载体、什么层级）——这是本类型特有的修复形态：不是改代码，是补知识的家。

## 实例

### 正例 1：操作类应知（两步法完整走一遍）

**第一步，LLM 生成应知清单**（从代码反推）：

```python
# src/db/session.py
engine = create_engine(os.environ["DATABASE_URL"])
# 代码旁证：conftest.py 里测试用的是 sqlite:///tests/fixtures/demo.db
```

应知清单条目（操作类）：「本地开发数据库如何获得——`DATABASE_URL` 指向哪个实例、demo 数据从哪来、是否有种子脚本」。

**第二步，比对载体**：agent 文档操作层（AGENTS.md）检索「database / db / 数据库 / seed」——零命中；注释检索——零命中。检索空白。

- 【信号档】LLM 两步法（压测点生成 + 载体比对空白）。
- 【证据等级】存在性候选（全类型最弱档）。真实情况可能是：本地要手工跑 `scripts/seed_demo.sh`（不在任何文档里）、要找运维要堡垒机上的只读账号——或者，也可能本地开发根本不需要数据库（有 mock），那就是应知清单生成时的误判。静态扫描区分不了这两种世界。
- 【agent 失败形态】agent 本地运行任务：起服务、连库、失败。它看到的报错是 `connection refused`——与「数据库配置错了」同形。它在 DATABASE_URL 的值上反复尝试（localhost、127.0.0.1、加端口），每一步都合理，每一步都错——因为它不知道「本地库要先 seed 脚本 + 堡垒机」这条**只存在于口头**的规则。失败无法归因：没有任何报错会提到「你没问对问题」。

```
DEBT.md 报告行（示意）
slug:          oral-tradition
location:      src/db/session.py::DATABASE_URL（关联载体：AGENTS.md 操作层，检索空白）
confidence:    低（存在性候选：连债的存在都是推断）
rationale:     应知清单条目「本地数据库获取方式」在 agent 文档/注释零覆盖
fix_suggestion: 外化建议——写入 AGENTS.md 操作层「本地环境」一节：seed 脚本路径 + 数据库获取方式
提议严重度带:   高（主轴：踩坑概率 = 环境可用性刚需 × 影响全部本地任务）
```

### 正例 2：概念类应知（领域模型空白）

```python
# src/domain/order.py
class Order:
    def submit(self):
        if self.channel == "partner":
            self.apply_partner_margin_rules()   # 这行为什么存在？
        ...
```

**第一步**，应知清单条目（概念类）：「partner 渠道订单的利润规则与普通订单的本质区别（业务概念）」。
**第二步**，对照领域模型文档（CONTEXT.md 类）——「partner」术语零定义；注释——零解释。

- 【信号档】LLM 两步法，概念类对照概念层文档，空白。
- 【证据等级】存在性候选。
- 【agent 失败形态】agent 接到「给 partner 渠道加个退款政策」的任务。它不知道 partner 订单的利润结构是「平台先扣点再分成」，于是把退款金额按普通订单逻辑计算——**代码写出来了、测试过了、上线错了**。可解性失败的深层形态：不是找不到代码，是找到了也理解不对，因为缺的是业务概念。

```
slug:          oral-tradition
location:      src/domain/order.py::Order.submit（关联载体：领域模型文档，术语 "partner" 检索空白）
confidence:    低（存在性候选）
fix_suggestion: 外化建议——写入领域模型文档概念层：partner 渠道定义与利润规则词条
提议严重度带:   中（概念类影响面广，但踩坑概率低于操作类刚需）
```

### 反例 1：implicit-contract 可覆盖的缺口（显式排除，不报）

```python
# src/cache/registry.py
def get_cache(key):
    # 代码注释里其实写着：
    # NOTE: 必须先调用 init_cache() 再用本函数，否则静默返回 None
    ...
```

「先 init 再用」确实是一条未写进任何 agent 文档的应知知识——但它的**痕迹在代码层**（注释 NOTE、防御检查、assert 消息）。族文件显式排除：implicit-contract（痕迹在代码里）可覆盖的缺口不在本类型。互斥声明（#51 / #53 双向对齐）：**零文字痕迹场景归 oral-tradition，有痕迹未外化归 implicit-contract**。分界逻辑：有痕迹就说明知识已经半外化了，债的形态是「没外化到接口声明面」，那是 implicit-contract 的判据；本类型专收彻底真空的。

### 反例 2：build-entry-unclear 可覆盖的缺口（显式排除，不报）

```
# 场景：本地跑测试前要先 docker compose up pg.yml（这个 compose 文件在文件系统里，
# 但没有任何文档声明「跑测试前要先起它」）
```

「跑测试前先起 PG」是一条应知知识没错，但**痕迹在文件系统里**（compose 文件存在、CI 里引用它）——build-entry-unclear 的 E4 档（延迟绕远/无本地 compose 声明）专门覆盖这类缺口。族文件显式排除它，E 族那边也对应不重复挂。分界逻辑同上：文件系统里有痕迹 = 可被其他类型的检测面锚定，口头传统只收全仓真空的。

## 边界与相邻类型

- **implicit-contract（E 族）**：以**痕迹所在层**分界——代码/测试/注释层有痕迹归 implicit-contract，任何载体无痕迹归本类型。两边判据互斥声明已双向对齐（#51 / #53）。
- **build-entry-unclear（E 族）**：痕迹在文件系统里（compose、CI、脚本）归它；本类型显式排除。E 族对应规则：compose 缺失信号让渡 E4，不重复挂。
- **agent-doc-missing（同族）**：那边报「代理上下文文档」这个载体的三态（缺失/过时/冲突）；本类型报「知识条目」的未覆盖。「文档在但没写这条」是外化缺口特例记本类型，但**概念类**缺口同时指向 agent-doc-missing 覆盖不足——两个视角（文档质量 vs 知识缺失）各报各的账。
- **doc-rot（同族）**：doc-rot 判「说了但说错」（注释分叉），本类型判「该说没说」。零重叠。
- **config-drift（D 族）**：配置键读取无源的失败形态（环境炸）与本类型的操作类条目很像，但 config-drift 判的是**验证回路配置可达性**（读取痕迹对撞六源），本类型判的是**知识外化空白**；同一场景（本地 DB 起不来）若 config-drift 的两端夹检测已能表达（读取痕迹 + 六源检索空白），D 族已报，本类型对应条目让渡，不重复挂同一失败形态。

## 讨论要点

1. **应知清单的生成边界是最大雾区**：LLM 压测点「从代码反推新人需要什么」没有客观 oracle——清单生成偏保守就漏报（口头传统天然隐蔽），偏激进就海量假阳性。族文件未给清单规模与分层配额的任何约束，这是执行时最需要实例校准的地方。
2. **假阳性的接受度**：族文件明示「README/docs 低可达知识接受假阳性」——讨论点：报告里是否给这类条目加「低可达外化已存在」的信号级标注，帮人裁哪些只需把 README 知识搬进 agent 文档（廉价修复）。
3. **存在性候选的报告语言**：全类型最弱档的定位要求报告行措辞极度克制（「候选」而非「债」）。DEBT.md 渲染时该类型的动词选择（「推断存在」vs「疑似」）需要单写手定死，避免与 B 族「脆性候选」混淆。
4. **与 agent-doc-missing 的概念类双挂**：「概念类缺口另指向 agent-doc-missing 覆盖不足」这句话的双挂语义族文件说得含糊——是同一条目两个 slug 并挂，还是两边各挂各的实例？按「零重叠、一实例一 slug」的族内规则字面理解有张力，建议 review 定音。
5. **反例 2 的让渡是单向的还是双向的**：C 族说 build-entry-unclear 可覆盖的缺口不在本类型；E 族对应句是「compose 缺失信号让渡 build-entry-unclear E4（不重复挂 config-drift）」——E 族这句写的是 config-drift 不是 oral-tradition。誊写发现：E 族分野规则里没有与 oral-tradition 的直接互斥句（只在 implicit-contract 一节带过「任何载体无痕迹 → oral-tradition」），C 族的显式排除句与 E 族的分野句**不对称**，建议在 E 族文件补一句对齐，避免两个子代理在「跑测试前要先起 PG」这类场景上重复报告。
