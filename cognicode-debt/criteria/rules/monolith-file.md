# monolith-file：巨石文件

> 判据权威来源：[E-process.md](../E-process.md) · 详解文档供人类讨论，子代理执行口径以族文件为准
> 所属族：[E 族：进程债](../E-process.md) · 失败模式：效率 + 可导航性 · 预排：高

## 规则陈述

这条规则说的是：**一个文件大到超出 agent 的有效理解预算，而且改任何一处都得通读全文件**。失败形态是「改一行要读五千行」——agent 接到一个看似很小的任务（改一个校验规则），却必须先在上下文里装进整个 5000 行文件，才能确定自己改的地方不会影响另外 4999 行。

两件事必须分开说清楚：

**第一，32K 是候选线，不是判罪线。** 确定性档用 token 估算（字符数 ≈ 4:1 折算）筛出超过 **32K** 参考线的文件——这个数字取的是「中位 agent 有效预算参考线」，其依据是：模型对长文件的有效理解质量衰减**远早于**上下文窗口上限（200K 窗口不等于 200K 都能同等质量地推理）。超线只是「值得 LLM 档进一步看」的候选资格；一个文件超了 32K 但修改高度局部（改哪读哪），它**不是本类型的债**。

**第二，判罪靠双层都过。** 体量五元组是第一层（它够大吗），LLM 修改局部性评估是第二层（它逼你全读吗）。两层合起来才是判据——**大不是罪，大且必须全读才是**。

为什么这是对 AI 不友好的债：人类面对巨石文件有一套隐性 coping 机制——折叠、搜索、肌肉记忆「这个函数大概在文件后半段」、只读熟悉的区块。agent 没有这些：它的「读」是逐 token 进上下文，巨石文件每次任务都全额收费；更糟的是**信噪比**——5000 行里与当前任务相关的 50 行被稀释在 1% 的浓度里，agent 的注意力被无关代码摊薄，改错位置、漏掉联动修改的概率随文件体量上升。传统 `code-smell` 的 agent 相关子集（超长函数、深嵌套、上帝类）与此同机制（都是上下文溢出），已并入本类型；美学子集（缩进、模式纯度）不收。

## 信号与判定

### 确定性档：体量事实五元组

五个静态可测的数字，对每个文件计算：

1. **token 估算**（字符数 ÷ 4）——主候选锚；
2. **符号数**——文件里定义了多少函数/类/变量；
3. **符号密度**（符号数 ÷ 行数）——密度极低的文件往往是数据文件或生成物；
4. **最大函数长度**——单个函数的行数极值；
5. **最大嵌套深度**——嵌套 if/for 的最深层数。

候选线 = token 估算超 32K 参考线。**排除项**：`@generated` 标记、vendored 目录、lockfile——它们也大，但 agent 不需要理解它们（不读、不搜、绕着走），与 duplicate-code 确定性档同口径。

五元组在报告里做**信号级标注，不进主轴**（见下文 rubric）。

### LLM 档：修改局部性评估

复用 module_depth.py 的判定协议（收集→prompt→单 JSON→重试→丢弃），回答一个问题：**「改一个典型任务需要读多少上下文？」**。这是判罪层：文件虽大，但如果典型修改（LLM 根据文件的职责推断典型任务）只涉及某个连续局部区块，那么需读上下文量远小于文件体量，不判债。

### 防换皮（本类型的灵魂规则）

传统 lint 报「函数太长 / 文件太大」，判的是**美学**（代码看起来不好）；本类型报「agent 改一处要读全文件」，判的是**失败形态**（agent 实际怎么死）。推论就是那条著名的分野：**高内聚巨文件传统报、我们不报**——一个 3000 行但职责单一、修改永远局部的文件，lint 会抱怨它，本类型必须放过它；一个 1800 行、五脏俱全、任何修改都要跨全文件理解的「中等身材上帝文件」，lint 可能放过它，本类型必须抓住它。锚定失败形态而不是锚定尺寸，是这条判据不变成「又一个 lint」的唯一办法。

### rubric

主轴 = **单次典型修改的上下文占比**（需读上下文量 ÷ 文件体量）：占比越高越严重。为什么用比值不用绝对值：绝对需读量受文件体量污染（大文件干啥都读得多），占比衡量的是「这个文件的结构把修改成本摊到了多广」——占比接近 1 意味着任何修改都是全文件事件；占比 0.15 意味着文件虽然大，但内部有良好的局部性边界。体量五元组退到信号级标注位，帮读者理解「这是个什么形状的巨物」，不参与排序。32K 参考线的精确校准留二期实证（动态测量 agent 实际 token 消耗）。

## 实例

### 正例 1：五脏俱全的上帝文件（超候选线 + 判罪成立）

```
src/web/middleware.py   —— 3,400 行 / 约 35K token（超 32K 候选线）/ 87 个符号
# 内容：认证 + 限流 + 日志格式化 + 请求 ID 生成 + CORS + 三个无关的
#       工具函数族，互相共享模块级可变状态 _request_ctx
# LLM 档典型任务评估：「给限流加一个按 API key 的维度」
#   → 需读：限流段 + _request_ctx 定义 + 认证段（_request_ctx 的写入方）
#          + 日志段（读取 _request_ctx）= 全文件约 85%
```

- 【信号档】确定性档·五元组（token 估算 35K 超 32K 候选线，另：最大函数长度 420 行、嵌套深度 7）→ LLM 档·修改局部性评估（典型修改需读 85%）。注意两层缺一不可：只超线（如高内聚查表文件）不判罪，只有局部性差但体量小也进不了候选线。
- 【证据等级】体量事实为确定性事实；判罪由 LLM 局部性评估给出，标置信度 0.83。
- 【agent 失败形态】agent 接任务「给限流加 API key 维度」，只读限流段就动手——它不知道认证段往 `_request_ctx` 里写了它依赖的字段，日志段又假设了该字段的存在；改动上线后日志链路静默丢字段。要么它谨慎地通读全文件，35K token 一次吃掉中位有效预算的大半，而其中 80% 与任务无关。两条路都是失败形态。
- 预期 DEBT.md 报告行：

```markdown
### monolith-file · src/web/middleware.py · 置信度 0.83 · 提议带：高
- 信号：体量五元组——35K token（超 32K 参考线）/ 87 符号 / 最大函数 420 行 / 嵌套深度 7（信号级标注）
- 判定：修改局部性评估——典型任务（限流加维度）需读约 85% 文件，上下文占比 0.85
- 提议修复：按职责拆为 auth / rate_limit / logging 三个模块，_request_ctx 显式化为参数对象
```

### 正例 2：超线巨物 + 修改全文件事件

```
src/legacy/importer.py   —— 5,400 行 / 约 41K token（超 32K 候选线）
# 一个巨型 main 循环（2,300 行）+ 模块顶部 300 行的模块级配置常量
# 散落在循环各处的隐式耦合（一个 flag 控制下游 6 处分支）

# LLM 档典型任务评估：「支持新的源格式 XLSX」
#   → 需读：巨型循环里格式分派段 + 该 flag 影响的全部 6 处分支 + 常量表 = 约 60%
```

- 【信号档】确定性档·token 估算 41K 超候选线 → LLM 档·局部性评估（需读 60%，且分散在 2,300 行循环的 6 个跳跃点）。
- 【证据等级】确定性事实（超线）+ LLM 评估标置信度 0.9。
- 【agent 失败形态】41K token 一进上下文，单文件就吃掉中位 agent 有效预算的绝大部分；6 处 flag 分支隔着几百行彼此不可见，agent 改了第 2 处漏了第 5 处，没有任何局部信号提示它还有遗漏——必须靠全文件通读自查，而全文件恰恰超出了它能有效推理的范围。
- 预期 DEBT.md 报告行：

```markdown
### monolith-file · src/legacy/importer.py · 置信度 0.9 · 提议带：高
- 信号：体量五元组——41K token（超 32K 参考线）/ 最大函数 2,300 行（信号级标注）
- 判定：修改局部性评估——典型任务（新增源格式）需读约 60%，分散于 6 个非邻接耦合点
- 提议修复：先做机械拆分（巨型循环按格式分派解体为 handler 注册表），不改行为
```

### 反例：高内聚大文件，占比低不报

```
src/nlp/tokenizer.py   —— 3,100 行 / 约 24K token / 超长查表数据段 + 算法主实现
# 结构：顶部 1,800 行确定性数据表（token 类型映射、例外词典），
#       底部 1,300 行自包含的 tokenizer 算法，数据与算法单向依赖、无交叉
# LLM 档典型任务评估：「新增一种 token 类型」
#   → 需读：数据表中相邻的映射段 + 算法中类型分派的 switch 段 = 约 12%
```

24K token 的大文件、lint 会皱眉、按传统「文件太长」审美必被点名——**不报 monolith-file**。

为什么不报：族文件防换皮规则白纸黑字：「**高内聚巨文件传统报、我们不报**」。这个文件大而内聚：数据段是被算法单向消费的静态表，算法段自包含；典型修改（加一种 token 类型）只触碰两个局部区块，LLM 档评估的上下文占比只有约 12%——「大」本身不构成失败形态，「大且必须全读」才是。主轴判的是占比，五元组只做信号级标注，所以它进不了报告；如果有一天它开始腐烂（数据与算法交叉引用、修改开始跨段），局部性评估会捕捉到占比上升，那时再报也不迟。

## 边界与相邻类型

- **shallow-module**（G 族，**互为镜像、不并挂**）：族文件显式分野——机制相反：monolith 是**一整个巨物**（太多东西挤在一个文件里，主轴 = 上下文占比高），shallow 是**太多薄层**（行为摊在层层 pass-through 里，主轴 = 性价比低）。两者 rubric 共用「上下文」语言但方向相反。一个仓库可以同时有巨物和薄壳（各报各的），但**同一个模块不会同时是两者**——要么一个文件塞了太多行为，要么一层目录摊薄了同一行为，互斥。
- **test-rot / flaky-test**（B 族，规模效应分野）：rot 的 skip 判据**用比例不用绝对数**、flaky 用**类别数不用计数**，都明确写了「绝对数受模块规模效应影响」——规模效应本身的债（测试太多、测试文件太大）归 monolith-file。反过来说，monolith-file 判源码文件为主，一个 12K token 的巨型测试文件同样可进候选（它也是 agent 需要读的文件），此时 rot/flaky/monolith 各报各的主轴，可多挂。
- **duplicate-code**（A 族）：同口径排除 @generated/vendored/lockfile，但债的形态不同——重复是「同样的内容出现多份」（结构信号），巨石是「不相关的内容挤成一份」（局部性信号）。一个巨石文件内部的大段自我重复理论上可双挂。
- **build-entry-unclear**（同族）：同属 E 族但无共享中间层。monolith 是「读不懂」，build-entry 是「跑不起来」，验证回路的不同环节，不混淆。

## 讨论要点

- **E 族概览表缺证据等级列**：B 族、G 族的族文件概览表都有「证据等级」列，E 族没有——本文一览表的证据等级一栏是从正文归纳的誊写补充。是疏漏还是有意（E 族四类型证据结构各异、难入一列）待确认；若是有意，建议族文件加一句说明，避免跨族誊写时各自发挥。
- **32K 参考线的校准**：族文件自己承认「精确校准留二期实证」。当前 32K 是拍定的中位 agent 有效预算假设——模型代际更替（有效预算快速上升）会让这条线漂移。建议在工程上把它做成可配置常量并在报告 rationale 里带上当时的取值。
- **「典型任务」的选择权**：LLM 档局部性评估依赖「典型任务」的定义——谁决定典型任务是什么？LLM 根据文件职责自行推断，还是从 git 历史的真实修改分布采样？后者更准但引入历史分析成本。族文件未说明，工程化前需要裁。
- **占比主轴的分母盲区**：需读上下文量 ÷ 文件体量——一个 40K 的文件需读 30%（12K 绝对量）与一个 8K 的文件需读 100%（8K 绝对量），主轴上后者更严重。但从 agent 实际成本看前者更贵。比值消掉了绝对成本的差异，是否需要在严重度带定档时把绝对量作为次级信号？族文件未讨论。
- **module_depth.py 协议的 LLM 不确定性**：复用的判定协议（收集→prompt→单 JSON→重试→丢弃）在原语境（deep/shallow 参考清单）里「LLM 的不确定性是特性」；但 monolith 判罪是产分路径，同一份不确定性现在是误差来源。两处对 LLM 判定的容错要求不同，复用时是否需要加校验层值得讨论。
