# misplaced-seam：错位 seam 债

> 判据权威来源：[G-architecture-shape.md](../G-architecture-shape.md) · 详解文档供人类讨论，子代理执行口径以族文件为准
> 所属族：[G 族：架构形状债](../G-architecture-shape.md) · 失败模式：变更安全性 + 可诊断性 · 预排：中

|---|---|---|---|

## 规则陈述

这条规则说的是：**想改一个行为，必须跨多个模块编辑**——行为没有家，散落在多个模块里；或者反过来，**模块的内部细节泄漏到了 seam 之外**，外部直接戳内部。对 agent 的失败形态是一句话：**改一处，漏一片**。它认为自己的修改是局部的（只动了一个文件、一个函数），实际还有一个必须同步修改的兄弟藏在另一个模块里——测试过了就自信提交，炸在别处。

为什么这对 agent 特别痛：agent 的变更安全边界是「我改的东西我看得见」。人类老手对隐式耦合有肌肉记忆（「动这个记得看下那边」），agent 没有——它只能依赖**静态可见的结构信号**来判断变更半径，而错位 seam 恰恰是结构信号说谎的形态：结构上分离（两个模块、两份文件），行为上耦合（必须一起改）。结构说「无关」，行为说「同类」，agent 信了结构。

**为什么主锚选 git 共编辑提升度**：判断「什么是一个行为」的最诚实证据，是人类/agent 实际改它时**动了哪些文件**——共编辑是行为的化石记录。自我报告的架构图会撒谎，目录结构会撒谎，但 git 历史不会：如果过去两年里每次改 billing 都要动 audit，那「billing 行为」物理上就横跨这两个模块，无论目录树怎么画。

## 信号与判定

### 双锚点（可各自或共同触发实例）

**主锚：git 共编辑提升度**（确定性档）

- 提取：`git log --numstat` 按模块分桶，统计每个模块对 A、B 的共编辑提升度——**lift = P(A∧B) / (P(A)·P(B))**。
- 为什么用 lift 不用共编辑计数：**消掉模块活跃度污染**。高频活跃模块（比如 utils）跟谁共编辑次数都多——那不是耦合，是它活跃。lift 是条件概率对独立性的偏离：lift ≫ 1 说明 A 和 B 同时被改的概率远超「各自独立活跃」能解释的程度，剩下的解释就是真耦合。
- 候选线 = lift 超阈 + **最小样本量**（如共编辑 < 5 次的对不报——lift 再高，2 次共编辑撑不起统计断言）。

**副锚：seam 泄漏**（确定性档，**确证子档**）

- 判定：B 模块的内部/私有符号被 A 跨模块引用。module-graph 工件的公开/私有符号清单可直接判。
- 为什么是确证：私有符号被跨模块引用是**静态事实**，不是嫌疑——不需要动态验证、不需要置信度，事实摆在 import 里。

**LLM 档（评估器）**：对提升度候选判「这对高频共编辑是否共享一个行为」，标置信度。设计已锁、实现与否看 DEBT.md 样例票成本。

### 证据等级

主锚是风险信号档（共编辑提升是统计事实，但「共享一个行为」是推断）；副锚泄漏子档是 G 族唯一的**确证**信号。

## 实例

### 正例 1：共编辑提升度（真行为横跨两模块）

```
git log --numstat 近两年的统计（示意）：
  P(billing 被改) = 0.12，P(audit 被改) = 0.08，P(billing ∧ audit) = 0.09
  lift = 0.09 / (0.12 × 0.08) = 9.4      ← 远超 1：共编辑概率是独立假设的 9 倍多
  样本：billing ∧ audit 共编辑 63 次      ← 最小样本量门槛轻松通过
```

- 【信号档】确定性档·提升度候选（lift 9.4、63 次共编辑）→ LLM 评估器判「计费规则变更必然牵动审计事件定义」共享一个行为，置信度 0.88。
- 【证据等级】风险信号 + 置信度（统计事实确凿、行为归属是推断）。
- 【agent 失败形态】agent 改「会员折扣的计算规则」：只动 billing/discount.py，跑测试全绿（audit 的测试不校验折扣语义），提交；一周后有人发现审计报表的折扣口径错了——行为「折扣」横跨两个模块，但结构、测试、文档都没提示这一点。
- 预期 DEBT.md 报告行：

```markdown
### misplaced-seam · billing ↔ audit 模块对 · 置信度 0.88 · 提议带：中
- 信号：共编辑提升度 lift=9.4（63 次共编辑，近 2 年）
- 定位：billing/discount.py ↔ audit/event_schema.py
- 评估：计费折扣语义与审计事件定义共享一个行为，seam 切在两模块之间
- 建议：折扣语义收进单一模块，或显式建立事件契约接口
- 信号级标注：共编辑频次 63（不进主轴）
```

### 正例 2：seam 泄漏（确证子档）

```python
# src/search/engine.py —— 跨模块引用 index 模块的私有符号
from src.index._posting_list import merge_postings   # ← _ 前缀私有符号，跨模块引用

def run_query(q):
    return merge_postings(lookup(q))
```

- 【信号档】确定性档·seam 泄漏：`_posting_list.merge_postings` 是 index 模块私有符号（`_` 前缀，无 `__all__` 覆盖），被 search 模块 import——静态事实。
- 【证据等级】**确证**（G 族唯一确证子档）——不需要置信度评估，事实摆在 import 里。
- 【agent 失败形态】index 维护者重构 posting list 内部表示（行为不变的深度化），不知道 search 在戳私有符号——因为「私有」的社交契约是「只有本模块用」。测试只跑 index 自己的，绿了就提交，search 的查询静默炸。
- 预期报告行：`misplaced-seam · search/engine.py ↔ index/_posting_list.py · 确证（泄漏） · 提议带：中`。

### 反例：活跃模块的高频共编辑（不报）

```
P(utils 被改) = 0.55，P(billing 被改) = 0.12，P(utils ∧ billing) = 0.068
lift = 0.068 / (0.55 × 0.12) = 1.03    ≈ 1：独立假设完全解释得通
```

**为什么不报**：utils 与 billing 共编辑次数绝对值很高（0.068 > 正例 1 的 0.09？同量级），但 lift ≈ 1——**提升度消掉了活跃度污染**，这正是判据不直接用共编辑计数的原因。utils 跟谁都共编辑，那是它活跃，不是它跟 billing 耦合。「传统审查报耦合度高（指标美学），本类型报 agent 改一处漏一片（失败形态）」——共编辑计数高但 lift 低的对，没有 agent 失败形态，不报。

## 边界与相邻类型

- **implicit-contract**：错位 seam 的「必须一起改」如果已经有文字/测试痕迹，可能同时是未声明契约——两 slug 可并挂（一个从架构形状说，一个从接口声明面说），修复建议互补。
- **test-shape**：seam 泄漏与 test-shape 的 import 私有同构，但主体不同——test-shape 是**测试**戳私有（债在测试侧），seam 泄漏是**生产代码**跨模块戳私有（债在模块边界）。一处是 `tests/` 里的 import，一处是 `src/` 里的 import。
- **shallow-module / hypothetical-seam（同族）**：shallow 是「薄」，misplaced 是「散」——薄壳层不改也会提高每次穿越成本，错位 seam 只在变更时爆炸；G 族内部三类型主轴各异，报告分组也不同（本类型归变更安全组）。

## 讨论要点

- **lift 阈值与最小样本量未定**（判据文件明示留技术选型）：9.4 明显、1.03 明显，但 2.5 算不算？5 次共编辑的门槛对本仓库（活跃度中等）是否合适？评审时建议给出直觉锚点。
- **LLM 评估器实现与否**：判据已锁（判什么），实现成本看 DEBT.md 样例票——若 MVP 不实现，提升度候选以「统计事实 + 无行为归属评估」的形态进报告，报告语言需要相应降级。
- **跨模块生产调用 vs 泄漏的灰区**：`src.index._posting_list` 若在 `__all__` 里声明了呢？「公开面声明优先」意味着它合法——那 seam 的划定本身就是这笔债的一部分，报告行应指向「seam 划错了」而不是「违规引用」。
