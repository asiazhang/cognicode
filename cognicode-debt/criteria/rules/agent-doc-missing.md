# agent-doc-missing：代理上下文文档缺失/撒谎

> 判据权威来源：[C-docs-knowledge.md](../C-docs-knowledge.md) · 详解文档供人类讨论，子代理执行口径以族文件为准
> 所属族：C 文档与知识债（[C-docs-knowledge.md](../C-docs-knowledge.md)）· 失败模式：可导航性 + 可解性 · 预排：高

## 一览

| 证据等级 | 检测档 | 实例粒度 | rubric 主轴 |
|---|---|---|---|
| 存在性：确证；过时：风险 + 置信度；冲突：风险 + 置信度（多文档并存未声明权威为确定性子档） | 确定性（存在性）+ LLM（过时/冲突） | 文档实例级（每个分叉/缺失的 agent 文档事实一个实例；概念层缺失置顶） | **误导方向**（一维）：撒谎 ＞ 缺失（缺失档内置顶概念层缺失） |

实例粒度族文件未显式定义，按判据对象（代理上下文文档及其断言）取文档级，见「讨论要点」。

## 规则陈述

这条规则说的是：**代理上下文文档——AGENTS.md、CLAUDE.md、CONTEXT.md、.cursorrules 这类专为编程 agent 准备的仓库说明——要么没有，要么在撒谎**。

要理解这个类型为什么预排高、且是「对 AI 最直接的债」，得先理解这类文档在 agent 工作流里的特殊地位。agent 冷启动的第一动作通常是读代理上下文文档（它是 agent 的「入职手册」，也是唯一的**第一信源**）——agent 对它的信任远高于普通文档，相当于人类新人把 onboarding 手册当真理。这个特殊地位带来两个后果：

1. **缺失 = agent 每次都从零开始**：不知道模块地图、不知道约定、不知道「先看哪里」。人类团队的老成员脑子里有仓库全图，agent 的全图只能靠这份文档建。知识没有家，agent 每个会话都要重新摸索——可导航性与可解性的双重损耗。其中**概念层缺失是最重的一档**：操作层的缺失（不知道跑什么命令）还能从代码/CI 里挖出来，概念层的缺失（术语、领域规则、模块职责的心智模型）没有任何代码可挖——「知识的家没建」。
2. **撒谎 = 误导被信任放大**：一份过时或自相矛盾的 agent 文档比没有更糟——agent 会把里面的断言当作已确认的事实去推理（同 doc-rot 的逻辑，但载体的信任级别更高，失败形态放大）。所以过时态的判据**从严**：第一信源上的错误断言，轻者也浪费 agent 轮次，重者把它引向完全错误的理解。

「撒谎」的两种形态：**过时**（曾经是真的，漂移了）与**冲突**（多份 agent 文档互相矛盾，或文档与代码相反）。冲突态的裁定规则是两层权威附则：含义类断言（术语/概念语义）——领域模型文档若存在则推定权威；行为类断言（命令/路径/函数行为）——**代码为事实**，但冲突只报分叉不裁方向，方向由人裁。

## 信号与判定

三态，检测档与证据等级各不同：

| 态 | 检测档 | 证据等级 | 判定 |
|---|---|---|---|
| **存在性** | 确定性 | 确证 | 代理上下文文档清单全缺失；**概念层缺失为置顶档位** |
| **过时** | LLM | 风险 + 置信度 | 只扫 agent 文档，判据从严（第一信源误导放大） |
| **冲突** | LLM 为主 | 风险 + 置信度 | 多文档互相矛盾或文档-代码相反；裁定规则 = 两层权威附则 |

- **存在性**（确定性档）：对照「代理上下文文档清单」（AGENTS.md / CLAUDE.md / CONTEXT.md / .cursorrules 等已知形态）做存在性检查。文件系统层面的事实，确证级，不需要 LLM。注意「全缺失」的语义分层：清单**一份都没有**是存在性态；**有文档但没有概念层**（只有操作命令、没有术语与领域模型）是存在性态内置顶档位——「知识的家没建」。
- **过时**（LLM 档）：文档里的断言与代码现实比对（目录结构变了、命令改了、模块重组了没更新文档）。只扫 agent 文档（不扫 README / docs/——那是 doc-rot 的雾区和 config-drift C3 的切面）。判据从严：因为载体是第一信源，**宁可多抓**。
- **冲突**（LLM 为主）：两个信源给出不兼容断言——CLAUDE.md 说「用 pnpm」，AGENTS.md 说「用 npm」；或文档说「入口在 src/main.py」而实际是 src/app.py。**多文档并存未声明权威 = 确定性子档**，归冲突态，不开第四态——这直接套用唯一真值原则：同一知识多份且未声明权威即债。裁定用两层权威附则，但行为类只报分叉不裁方向。

报告行按主轴排序：撒谎（过时/冲突）＞ 缺失；缺失档内置顶概念层缺失。

## 实例

### 正例 1：存在性——全缺失（确证）

```
仓库根目录：README.md, package.json, src/, tests/ ……
AGENTS.md   （不存在）
CLAUDE.md   （不存在）
CONTEXT.md  （不存在）
.cursorrules（不存在）
```

一个 6 万行的 monorepo，代理上下文文档清单全部检索空白。

- 【信号档】确定性档：存在性检查。
- 【证据等级】确证（文件不存在是客观事实）。
- 【agent 失败形态】agent 冷启动只能 `ls` + 读 README + 猜。每个任务都在重建同一张仓库地图：找入口靠试、找模块靠检索、找约定靠从代码反推——全部撞 oral-tradition 的坑（文档缺失是口头传统的温床）。可导航性失败是每个会话的固定开销。

```
DEBT.md 报告行（示意）
slug:          agent-doc-missing
location:      仓库根目录（代理上下文文档清单全缺失）
confidence:    高（确证：存在性）
rationale:     AGENTS.md/CLAUDE.md/CONTEXT.md/.cursorrules 全部不存在
fix_suggestion: 建立 agent 上下文文档，先立概念层（术语表 + 模块地图），再补操作层
提议严重度带:   高（主轴：缺失档）
```

### 正例 2：存在性——概念层缺失（置顶档位）

```markdown
# AGENTS.md（存在，但没有概念层）
## 命令
- 测试：pnpm test
- 构建：pnpm build
（全文完——没有术语表、没有模块职责、没有领域规则、没有架构图）
```

- 【信号档】确定性档存在性检查通过（文档在），但 LLM 档判读发现**概念层真空**。
- 【证据等级】存在性确证（概念层缺失是文档结构的事实）。
- 【agent 失败形态】agent 知道怎么跑测试，但接到「修改 partner 渠道的分成逻辑」时：什么是 partner？分成规则在哪、归谁管？文档零概念，代码零注释——agent 只能全库语义搜索「partner」，然后逐文件读业务代码反推领域模型。操作层缺失让 agent 慢，**概念层缺失让 agent 理解错**——后者才制造静默错误（按错误的心智模型写出能通过测试的错代码）。

```
slug:          agent-doc-missing
location:      AGENTS.md（概念层缺失——只有操作命令，无术语/模块职责/领域规则）
confidence:    高（确证：概念层缺失）
fix_suggestion: 在 AGENTS.md 补概念层；或按本仓库先例拆 CONTEXT.md 专门承载领域模型（两层权威附则的推定权威）
提议严重度带:   高（主轴：缺失档内置顶概念层缺失）
```

### 正例 3：过时——第一信源撒谎（风险 + 置信度，判据从严）

```markdown
# AGENTS.md
## 仓库结构
- src/api/        所有 REST 端点（实际：半年前已拆到 src/services/*/routes.py）
- src/core.py     核心领域逻辑（实际：已拆成 src/domain/ 包，core.py 只剩 shim）
```

- 【信号档】LLM 档：文档断言与当前目录结构比对。
- 【证据等级】风险 + 置信度高。
- 【agent 失败形态】agent 按手册直接去 `src/api/` 找端点——目录不存在，或存在但是空的。因为信任第一信源，agent 的第一反应不是「文档错了」而是「我找的方式不对」，在错误的自我怀疑里烧轮次。可导航性失败 + 可解性失败连锁。

```
slug:          agent-doc-missing
location:      AGENTS.md「仓库结构」一节
confidence:    中（风险信号：过时，LLM 推断——目录已重组）
fix_suggestion: 更新结构描述；建议加「以 tree 输出为准」的轻断言降低未来漂移面
提议严重度带:   高（主轴：撒谎 ＞ 缺失；第一信源误导放大）
```

### 正例 4：冲突——多文档矛盾（含确定性子档）

```markdown
# CLAUDE.md
包管理器统一用 pnpm。禁止 npm install。

# AGENTS.md
安装依赖：npm install
```

- 【信号档】确定性子档：多 agent 文档并存且未声明权威（唯一真值原则直接命中）；LLM 档补裁「两个断言是否真的互斥」。
- 【证据等级】并存未声明权威为确定性事实；互斥性为 LLM 判定（本例命令互斥，置信度高）。
- 【agent 失败形态】两个信源打架，agent 无所适从——它会随机信一个（通常按文件名与自身生态的亲和度，Claude 系信 CLAUDE.md、其他信 AGENTS.md），装出**混合环境**：node_modules 同时被 pnpm 和 npm 写过，依赖树悄然分叉，后续构建报错与归因彻底脱钩。这不是浪费一次尝试，是**静默污染**。

```
slug:          agent-doc-missing
location:      CLAUDE.md「包管理器」× AGENTS.md「安装依赖」（未声明权威）
confidence:    高（并存未声明权威：确定性子档；互斥判定：LLM 高置信）
fix_suggestion: 声明权威载体（AGENTS.md 或 CLAUDE.md 之一为主，另一份引用），其余向权威合并
提议严重度带:   高（主轴：撒谎档；行为类冲突——只报分叉，方向由人裁）
```

### 反例：README 过时不是本类型的债（不报）

```
# README.md（非代理上下文文档）
## 快速开始
npm run start     # 实际脚本已改名 npm run dev
```

README 不是代理上下文文档——它不在存在性清单里，它的断言分叉不落本类型的三态。按 C 族的检测面聚焦（#51 决策 1），README 长文档信号整体在雾区；其中**配置断言**切面归 config-drift C3（D 族），其他长文档信号留册待二期。分野规则明文：代理上下文文档的三态专属本类型，doc-rot MVP 只走注释通道——**与 doc-rot 零重叠，与 README 零关系**。这个反例的意义在防换皮：不能因为「也是文档、也过时、agent 也可能读」就扩进来——判据锚定的是**第一信源**这个特殊信任地位，不是「文档」这个载体大类。

## 边界与相邻类型

- **doc-rot（同族，零重叠）**：载体切分——代理上下文文档的三态专属本类型，doc-rot MVP 只走**注释**通道。唯一交叠句：「多文档冲突同时构成注释分叉时各挂各的」（各开各的实例，不算双挂同一实例）。
- **oral-tradition（同族）**：本类型报「文档载体」的状态（缺失/过时/冲突），oral-tradition 报「知识条目」的未覆盖。AGENTS.md 存在但没写「本地 DB 要先 seed」——载体过时态可能不命中（文档说的都还是对的），知识条目命中 oral-tradition；AGENTS.md 概念层缺失——载体命中本类型置顶档，具体概念条目的空白同时是 oral-tradition 的候选。两边各报各的账。
- **build-entry-unclear（E 族）**：E2 声明碎片化（多源命令不一致）与本类型冲突态形似——分界在载体与判据：E2 说的「源」是 package.json / CI / agent 文档等**入口声明面**的碎片化，本类型冲突态说的是**代理上下文文档之间/与代码**的矛盾；同一份 CLAUDE.md 与 AGENTS.md 的包管理器矛盾在两边都可能被看到，按「入口声明」语境归 E2、「第一信源信任」语境归本类型——誊写发现此分野需要 review 定音（见讨论要点 4）。
- **两层权威附则**：本类型冲突态的裁定规则即附则本身——含义类：领域模型文档（概念层）推定权威；行为类：代码为事实、只报分叉。修复建议对行为类冲突双写（改文档或改代码，方向由人裁）。

## 讨论要点

1. **概念层的判定标准缺句**：置顶档位「概念层缺失」没有操作性定义（多大体量算概念层？有没有术语表就行？）。建议参照本仓库先例（CONTEXT.md 的词条结构）定一个最小骨架清单，否则确定性档判不了「有文档但无概念层」，会全压到 LLM 档。
2. **存在性态的「全缺失」粒度**：清单全缺失报一个仓库级实例（同 build-entry-unclear E1 的仓库级单点置顶先例），还是按缺失的载体形态分列？族文件未说。仓库级单点更符合「知识的家没建」的语义，但销账粒度（补了 AGENTS.md 但 CLAUDE.md 仍缺）会粗。
3. **过时态「判据从严」缺操作化**：从严 = 置信度阈值更低就报？还是断言漂移的敏感度更高（目录改名即报）？从严到什么程度会与 doc-rot 注释通道的判读口径打架（同一漂移注释报、文档不报，或反过来），需要实例校准。
4. **与 build-entry-unclear E2 的载体交叠**（誊写发现的潜在矛盾）：C 族说本类型只管代理上下文文档，E 族 E2 说「package.json 说 npm、CI 用 pnpm」的碎片化归它——但 agent 文档也是 E2 的「源」之一。同一处 CLAUDE.md/AGENTS.md 矛盾，两边判据都能命中。C 族零重叠句只对 doc-rot 说了，对 E2 没说。建议补一条：涉及构建/测试命令的文档矛盾归 E2，涉及其他断言（结构、概念、约定）的归本类型——或明确允许双挂。
5. **.cursorrules 等形态的清单维护**：代理上下文文档的形态清单本身在快速演化（新 agent 工具层出不穷），清单谁来维护、新形态如何进清单，属于工程边界但影响存在性态的召回，建议随 SKILL.md 版本化。
