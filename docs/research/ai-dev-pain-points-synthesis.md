# 双模型交叉验证综合结论：AI 开发时代的痛点全景

> 票：[AI 开发软件时代的痛点与问题全景 #48](https://github.com/asiazhang/cognicode/issues/48) · 地图：[#39](https://github.com/asiazhang/cognicode/issues/39)
> 本文是两份独立调研的**交叉比对结论**，供后续讨论与 [撰写重定位决策文档 #44](https://github.com/asiazhang/cognicode/issues/44) 直接引用：

> - [`ai-dev-pain-points-ds.md`](./ai-dev-pain-points-ds.md)（DeepSeek V4.1 Flash 版）：含证据分级、16 项判别表、三条判别法则

> 两份调研由互不知晓对方结论的代理并行完成；本文把结果分成三层：**双源一致**（高置信，可直接进决策文档）、**单边独有**（有价值的增量，采信前可讨论）、**对决策文档的直接输入**。

## 一、双源一致发现（高置信）

1. **核心图景一致**：AI 把「写代码」变便宜，瓶颈全部后移到验证、理解与让下一个 agent 别踩坑。产出暴涨的同时 review 负担、质量滑坡、事故率恶化——四组互不隶属的数据源同向（DORA、GitClear、Faros、CodeRabbit）。
2. **METR RCT 及其反转**：早期-2025 工具使资深开发者慢 19% 且感知完全失真；2026-02 更新显示晚期-2025 工具原始数据转正（弱证据，选择偏差严重）。**任何「AI 让开发者变快/变慢 X%」的静态结论都不可作为长期前提**。
3. **「表面可信」是贯穿两端的主线**：AI 代码风格得体、失败藏在表面之下（Faros/CodeRabbit 1.7x 问题率），人类 review 惯用的气味信号失效，必须切换到「重建意图」的高强度认知模式。
4. **判别结论一致**。指向「对 AI 不友好的债」的核心痛点收敛于：
   - 部落知识未外化（agent 无「地图」）
   - 隐藏变更耦合（改 A 必须改 B，代码里看不出来）
   - 重复逻辑多份真源
   - 验证回路缺失/慢（缺测试、测试慢、环境装不上）
   - 过时文档与死代码的主动误导
   - 巨型文件/浅模块
   - flaky 环境（DS 版补：对 agent 是双向伤害——误判失败/误判成功）

   明确**不指向**的也一致：review 容量、junior 技能萎缩、治理缺口、生成侧安全漏洞、幻觉 API（模型问题非仓库债）。
5. **空档一致**：所有既有解法（linter/SonarQube/CodeScene/context engineering/AGENTS.md/AI review）都在「改代码的人或 AI」侧发力，**没有任何工具以「下一个 agent 的实际表现」为判据做仓库级存量债识别**——与 [`debt-taxonomy.md`](./debt-taxonomy.md) 的学术空档论断（所有既有体系的利息受损者都是人类）互为正反面。

## 二、单边独有发现（值得采信的增量，讨论点）

### DS 版独有

- **ETH Zurich AGENTS.md 实验 + Meta 反驳**（关键证据对）：手写 context 文件平均仅 +4%、LLM 生成的 -3%、推理成本 +20%；但 Meta 在专有代码库上以 59 份上下文文件实现覆盖 5%→100%、agent 工具调用/token **-40%**。分歧本身暴露最大空白：**context 文件有效性高度依赖仓库，而业界无验证手段**——「这份 AGENTS.md 在该仓库上到底有没有用」无人能回答。
- **三条可复用判别法则**：
  1. **换主体测试**：把受损方从「人类维护者」换成「下一个 agent」，痛感是否仍然成立且可观测？
  2. **产物 vs 判据**：社会债/人员债的产物（文档、规范）恰是 agent 导航所依赖的，但判据（人员分布、知识流失）与 agent 无关——只取产物、不取判据。
  3. **产出缺陷 ≠ 仓库债**：换一个更强的模型重跑同一任务，痛感消失 → 生成质量问题；不消失 → 仓库债。
- **市场侧证据**：55% 工程负责人把「代码库理解」列为头号担忧且自认无 review 之外的应对（Augment 219 人）；AI 已占已提交代码 42%（Sonar 2026）；「vibe code cleanup」人力外包已出现且付费——需求真实但无标准度量。

### GLM 版独有

- **Sourcegraph CodeScaleBench 五种结构化失败模式**（1,281 次 agent 运行）：迷路、错文件/错符号、跨文件改动失手、工具空转、context 溢出；且证明是「context 问题不是智力问题」——为债的严重度模型提供现成测量范式。
- **概念层词汇**：Osmani 的 comprehension debt（理解债）、MIT 的 cognitive debt（认知债），为叙事提供现成词汇。
- **Anthropic 40 万会话研究**：「91% 的可见解决仍需用户显式纠正」——agent 的失败由人兜底，兜底能力 = 对仓库的理解深度。

## 三、对决策文档的直接输入（#44 引用）

- **「为什么是现在」三重证据**：
  - 体量：AI 占已提交代码 42%（Sonar 2026）、Google 新代码 75%（2026-04）、GitHub PR 量三年 5 倍
  - 决策层确认：55% 头号担忧（Augment）、57% review 队列 + 49% 规格清晰度（Madrona）、92% 治理挑战（GitLab）
  - 既有解法被证伪：AI 审 AI 拒收率 56.3%（31,073 条实证）、AGENTS.md 在通用开源库上边际/负收益（ETH）
- **首发债项候选**（双源判别表收敛，与 [`debt-types.md`](./debt-types.md) 的 A–G 族对表）：部落知识缺失、隐式变更耦合、重复逻辑、验证回路缺失、主动误导文档/死代码、巨型文件/浅模块、flaky 环境。
- **叙事分工**：个人开发者讲 agent 迷路/跨文件失手，团队负责人讲 review 负担/质量滑坡/事故率——两端痛点不同但指向同一批债项，支撑「双受众、单一债清单」的产品结构。
- **必须写进文档的风险声明**：
  - agent 能力在快速上升（METR 反转、debug 会话占比七个月减半），CogniCode 的赌注是「**仓库属性造成的失败不随模型进步消失**」（context 问题不是智力问题），且测量须能随模型版本重跑，不能固化成静态规则清单。
  - 厂商数据不可作为独立验证：所有「倍数级」数字方向一致但幅度存疑；对外叙述应以可复现的自家测量为主证据，行业报告只作背景。
  - 「代码库理解」痛点中有一部分不可债化（需求模糊、规格缺失），属 agent 输入侧，交给 spec-driven 工具链；CogniCode 只覆盖「实现与文档矛盾」这个可债化子集。

## 讨论入口

针对本文，建议讨论聚焦在三个开放点：

1. **ETH vs Meta 的分歧**：CogniCode 是否应该把「context 文件有效性验证」纳入产品范围？（DS 版认为这是最贴合能力边界的机会点；但可能与「债识别」的主定位有张力。）
2. **首发债项候选的取舍**：七个候选里 flaky 环境的确定性检测难度最高，是否进首发？
3. **风险声明的表述**：「仓库属性造成的失败不随模型进步消失」是核心赌注，如何写才不会被「下一代模型解决一切」的叙事反噬？
